# WT Mod Manager — доверенные Windows-релизы (Beta 11)

Эта схема не скрывает угрозы от Windows и не отключает Microsoft Defender.
Цель — прозрачный, проверяемый и воспроизводимый по **процессу** выпуск.

## Что гарантируют новые проверки

1. Build job запускается на Windows x64 из точного Git commit и собирает
   переносимую версию и полноценный установщик.
2. Тесты Python, GUI и реальная тестовая установка/запуск/удаление должны пройти.
3. Сверяются версии в Python, Inno Setup, GitHub Actions и release notes.
4. Проверяется статус Authenticode на **обоих** распространяемых EXE.
   Один подписанный, другой неподписанный — ошибка публикации.
5. Создаются `SHA256SUMS.txt` и `build-info.json` с версией, временем сборки,
   исходным commit, GitHub Actions run, SHA-256, размерами и подписью.
6. GitHub Actions `actions/attest@v4` генерирует SLSA build provenance для
   опубликованных файлов. Установщик и EXE повторно проходят аттестацию
   с помощью GitHub CLI перед публикацией.
7. Отдельный publish job с ограниченным правом `contents: write` запускается
   **только после успешного build job** в ветке `main`.
8. Существующий release/tag не перезаписывается. Чтобы выпустить следующую
   версию, необходимо повысить номер версии во всех согласованных местах.

Такая схема подтверждает происхождение файлов и отсутствие изменений
между сборкой, хешированием и публикацией. Она не доказывает отсутствие
любых вредоносных функций.

## Как проверить опубликованный файл

После загрузки только с официального GitHub Releases:
```powershell
Get-FileHash .\WTModManager-Setup.exe -Algorithm SHA256
```
Сравните значение с `SHA256SUMS.txt` и `build-info.json` того же релиза.

Для проверки происхождения через GitHub CLI:
```powershell
gh attestation verify .\WTModManager-Setup.exe --repo qwerthegoe-hash/WT-Mod-Manager-Website
```
И для проверки подписи издателя (когда появится сертификат):
```powershell
Get-AuthenticodeSignature .\WTModManager-Setup.exe | Format-List Status,SignerCertificate,TimeStamperCertificate
```

Важно: **аттестация GitHub — не Authenticode-подпись Windows**. Поэтому она
сама по себе не избавит от SmartScreen.

## Настоящая цифровая подпись Authenticode

Скрипт `tools/sign_windows_release.ps1` уже поддерживает доверенный
PFX-сертификат, если он действительно доступен для экспортируемого
подписания. Владелец проекта самостоятельно подключает GitHub Actions secrets:
- `WTMM_SIGN_PFX_BASE64` — действительный PFX, кодированный Base64.
- `WTMM_SIGN_PFX_PASSWORD` — пароль к этому PFX.

Secrets используются только в CI для main; исходники, PR и EXE не содержат
ключа подписи. Исполняемый файл, нативный DLL и установщик подписываются
до создания хешей и аттестаций. Сломанная подпись приводит к остановке
публикации. Если оба секрета отсутствуют, релиз честно обозначается
**unsigned**. Если указан только один секрет — сборка падает с ошибкой.

У современных удостоверяющих центров ключи часто защищены HSM и не
экспортируются как PFX. В таком случае потребуется **отдельная интеграция**
облачной подписи, а не попытка вытащить закрытый ключ.

Возможные официальные пути:
- Публикация MSIX через Microsoft Store (Store подписывает такой пакет).
  Наша текущая форма — Inno Setup EXE, так что требуется отдельная
  подготовка MSIX; существующий EXE не становится подписанным автоматически.
- OV-сертификат для разработчика/издателя, соответствующего требованиям CA.
- SignPath Foundation для подходящих открытых проектов — необходимо
  отдельно подать заявку и пройти проверку. Доступность не гарантирована.

Нельзя получать сертификат, используя чужую или ложную личность. Процесс
проверки издателя может требовать официальных документов и участия
законного представителя.

Официальная информация:
- https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options
- https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation
- https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations

## Ложные срабатывания VirusTotal / Defender

1. **Не отключайте защиту и не добавляйте исключения** ради запуска EXE.
2. Сверьте официальный SHA-256, GitHub provenance и, если доступна, подпись.
3. Проверьте, какой именно антивирус обнаружил угрозу и как называется
   его определение. Одно срабатывание среди многих **не является**
   доказательством заражения или безопасности.
4. Изолируйте факты без выполнения подозрительного файла: контрольная сумма,
   версия, официальный URL релиза, результаты сканирования и отчет проверки.
5. Если обнаружение похоже на ложное, отправьте файл **производителю именно
   этого антивируса** на официальную проверку. Не пытайтесь «маскировать»
   файл ради исчезновения предупреждений.
6. При реальном обнаружении остановите публикацию, разберите причину,
   устраните проблему и соберите новую версию.

См. https://docs.virustotal.com/docs/false-positive

## Что нельзя обещать

- Сертификат и GitHub attestation не дают автоматической положительной
  репутации SmartScreen новым EXE.
- Отсутствие предупреждений у большинства антивирусов не означает
  безусловной безопасности.
- PyInstaller `--onefile` остаётся удобной упаковкой; это не шифрование.
- Сборки проверены по процессу, но не обязательно **бит-в-бит идентичны**
  при повторном построении на другом Windows-образе.
- Пока издатель не получил сертификат и не настроил подпись, GitHub
  публикует unsigned тестовые сборки с честным обозначением этого факта.
