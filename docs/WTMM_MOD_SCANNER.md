# WT Mod Scanner — серверная очередь проверок

После загрузки файла в закрытый каталог Supabase Storage запись мода ставится
в приватную очередь. PostgreSQL и Supabase Edge Functions проверяют не больше
одного ZIP одновременно: пять архивов будут обрабатываться последовательно.

Задача Cron вызывается раз в минуту. Каждое выполнение забирает ровно одну
заявку. Для каждого задания предусмотрено до трёх попыток и восстановление
зависшей проверки. В Vault хранится случайный секрет вызова; публичный сайт
и обычные пользователи не могут управлять очередью.

Проверки: корректность центральной директории ZIP, имён и локальных заголовков;
CRC файлов, содержимое без исполнения, лимиты на сжатие, подозрительные
расширения и сигнатуры исполняемых файлов, дубликаты и символические ссылки.
Ограничения: ZIP 20 МиБ, до 250 элементов, до 80 МиБ распаковки.
Небезопасные архивы блокируются, ошибки инфраструктуры повторяются.

Статусы на сайте: в очереди; сканирование; структура ZIP проверена;
заблокировано; временная ошибка.

Это структурная проверка, НЕ гарантия отсутствия вирусов и НЕ разрешение
на автоматическую публикацию. После неё по-прежнему требуется проверка и
действие модератора. Дополнительный ClamAV-сканер присутствует в workflow
scan-mod-packages.yml, но его автоматический запуск требует настройки
защищённых GitHub Secrets и переменной WTMM_SCAN_ENABLED=true.

Файлы проекта:
- docs/database/mod_scan_sequential_queue.sql — структура очереди и RPC.
- docs/database/mod_scan_antivirus_approval_guard.sql — барьер модерации.
- supabase/functions/wtmm-mod-scan — серверный ZIP-сканер.
- docs/database/mod_scan_cron_schedule.sql — расписание.
- docs/mods/mods.js — статусы, сообщения и действия модератора.

Проверка развертывания: активный Cron wtmm-mod-scan-serial, HTTP 200 с
ответом processed:0 при пустой очереди; Deno ZIP-тесты и CI.
Полный сквозной тест с реальной загруженной заявкой пока не выполнялся.
